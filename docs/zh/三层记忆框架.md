# 三层记忆框架 —— 技术说明书

> 版本：2026-10-28（经历层 / episodes）
> 代码：`memory_store.py`（688 行 / 41.4 KB）、`memory.mjs`（174 行 / 12.4 KB）、`mcp_server.py` 记忆段
> 记忆工具：9 个（`bili_memory_*` 8 个 + `bili_experience_search` 1 个）
> 数据目录：`<home>/.dsh/bili-duty/memory/`

---

## 1. 它解决的问题

私信轮每一轮都是**全新的 headless 进程**，跑完即死。

没有这套东西时：
- 每轮只能看到"最近 20 条对话"，再往前真的忘了
- 想记住更多只能塞更长上下文，而窗口有硬上限
- 塞到极限后模型开始丢中间信息（注意力稀释）

**一句话**：把"能记住多少"从**上下文窗口**问题，变成**存储 + 检索**问题。

---

## 2. 三层

| 层 | 存什么 | 上限 | 怎么用 | 更新方式 |
|---|---|---|---|---|
| **L1 核心画像** | 身份、明确偏好、关系 | **≤5210 字节**（当前 209） | **每轮全文注入** | `bili_memory_l1` 整份重写，格式 `标签：内容` |
| **L2 长期记忆** | **事实**（high/mid/low）+ **经历**（episodes） | 无总条数上限；每轮注入 **≤6144 字节**相关卡片 | 按当前话题挑卡片；细节按需展开 | `bili_memory_commit`，每轮 facts 0–2 条、episodes 0–3 段 |
| **L3 原始历史** | 每条消息原文（只追加） | 无限（当前 190 行） | **只检索**，不解码进上下文 | `bili_memory_ingest` 自动 |

### 2.1 文件与角色

```
memory/
  L1-<uid>.md          核心画像（自由文本，标签格式）
  facts/<uid>.md       L2 渲染投影（派生文件，不要手改）
  <uid>.state.json     真相：facts / episodes / tasks / operations
  <uid>.pending.json   事务进行中存在，崩溃后恢复用
  history/<uid>.jsonl  L3 原文（只追加）
  backups/             每次整理前的整份备份
```

> **关键**：`state.json` 是真相，`facts.md` 只是投影。改 md 会被下一次渲染覆盖。

### 2.2 经历（episode）的结构

```
title            一句话主题
summary          ≤600 字节梗概
topics / aliases 检索用的关键词与别名
sources          来源 msg_id 列表（必须真实存在）
importance       {explicit, commitment, change, emotion} 各 0–3
importance_reason 给分的理由（模型的判断，不是系统理解）
details          {context, user_view, assistant_view, turning_point,
                  interpretation, unresolved}
quotes           [{msg_id, text}] 逐字引文（必须能在来源中逐字找到）
revision         版本号，补充不覆盖
```

**细节预算由重要性档位决定**：brief 1200 / standard 3600 / deep 8000 字节。

---

## 3. 四条数据流

```
① 写：  收到消息 → 原文进 L3（真实 msg_id）→ 本轮结束提交 0–3 条 L2
② 读：  L1（全量）+ L2（按话题挑 ≤6144B）+ 最近 20 条 + L3 检索命中（≤6 条）
③ 升级：L3 翻到旧事 → bili_memory_promote → 抄进 L2（L3 原文不动）
④ 整理：L2 重复过多 → bili_memory_compact 局部合并（必须给 merge_ids，保留全部来源）
```

---

## 4. 九个机制

| # | 机制 | 作用 |
|---|---|---|
| 1 | **可逆性** | 原文永不删改；压缩失败也能从 L3 找回 |
| 2 | **来源可追溯** | 每条带 `msg_id`，`bili_memory_read` 可展开上下文与历史版本 |
| 3 | **事实/推测分离** | 推测必须标；L1 里只能进「推测特征」，代码级拦截 |
| 4 | **纠正链** | `replaces` 指向被推翻结论；旧结论不可复活 |
| 5 | **经历版本 revision** | 补充不覆盖，旧版本可读回 |
| 6 | **三维度分离** | 重要性 ≠ 保留深度 ≠ 本轮相关性 |
| 7 | **再巩固只认新证据** | 自己搜索/回忆**不算**又经历一次（防自我强化误解） |
| 8 | **引文逐字校验** | 引文必须能在来源消息里逐字找到，编造拒收 |
| 9 | **隔离** | 自己的观看报告（`bili_experience_search`）与联系人私信画像互不污染 |

## 5. 升级依据（3→2 / 2→1）

### 5.1 L3 → L2

| 路径 | 触发条件 |
|---|---|
| 自动 | 本轮 L2 **无相关命中**时才扫 L3（有命中就不扫，省预算） |
| 主动 | `bili_memory_search(layer="history")` / `bili_memory_read` |
| 升级 | `bili_memory_promote(msg_id, …, evidence_msg_id, memory_id)` |

**判定规则（提示词原文）**：

> **单纯想起旧事不会提升重要性。对方新消息再次提起才可补充经历。**

**经历重要性四维度（各 0–3）**：
`explicit`（明确要求记住）、`commitment`（约定）、`change`（观点/关系转变）、`emotion`（明确表达的情绪）。
必须写 `importance_reason`；**按证据判断，不按聊天句数或检索次数打分**。

**代码硬约束**：`msg_id` 必须存在于历史；证据必须存在；同样调用判重。

### 5.2 L2 → L1

> **明确的新证据改变核心画像时**，才用 `bili_memory_l1` 整份更新，**保留无关的已有内容**。

| 约束 | 内容 |
|---|---|
| 只放什么 | 稳定身份、明确偏好、关系（不是"聊过什么"） |
| 推测 | **只能放「推测特征：」**，代码拦截 |
| 格式 | 每行 `标签：内容`，标签 1–12 字 |
| 大小 | ≤5210 字节 |

**这是全系统最保守的一环。**

### 5.3 谁在判断

**模型判断，代码只保证"有据可查"**：
- 代码管：来源真实性、格式合法性、防编造、防重复、防篡改
- 模型管：值不值得记、重要度几分、为什么

**唯一客观信号**：跨日再提及（代码按 `last_date` 判断）。
**刻意排除**：不按句数、不按检索次数（防"自己回忆一次就算又重要一次"）。

## 6. 优势

1. **单轮上下文恒定，历史无限**——当前注入约 5 KB，聊三年还是这个数
2. **抗"越总结越糊"**——论文预测：反复不可逆摘要的误差随压缩次数**超线性**增长，可逆存档则持平。实测印证：59 条事实挤在 4096 字节里，**只有 13 条可见**
3. **可纠正、可追责**——一句"你上次说……"能查到具体 msg_id 和原文
4. **故障可见**——`archive / reply / memory` 三态独立记录；回复失败不影响记忆，记忆失败不重发消息
5. **对话优先**——私信 > @ > 刷视频；长轮次期间检测不断（10 秒一轮询）

---

## 7. 劣势 / 代价

1. **复杂度高**——41 KB 核心 + 9 个工具 + 6 个文件。一天之内出过 3 次崩溃（字段覆盖、坏事务、ID 精度）
2. **双文件一致性**——`state.json`（真相）与 `facts.md`（投影）之间存在窗口；有 WAL 兜底，但"md 落后于 state"仍可能
3. **强约束带来摩擦**——每条事实必须来自真实消息，她**没法凭印象记东西**（L1 是唯一例外）
4. **检索是字面匹配，不是语义**——"上次那个让我心里一动的片子"搜不到，除非原文有这几个字。**目前最大功能缺口**
5. **规则靠模型自律**——"每轮 ≤3 条""引文逐字"只能**拒收**，不能**自动补全**
6. **成本**——每轮约 5 KB 注入 + 偶发 read/export；整理需额外模型轮
7. **单一模型自产自销**——写记忆和读记忆是同一个模型；机制 7 缓解但未根治

---

## 8. 不足（未实现）

| 缺口 | 影响 |
|---|---|
| **经历层目前为空** | 13 条旧事实是"结论"，无转折无引文；经历从 2026-10-28 起才积累 |
| **无语义检索** | 字面关键词的天然上限 |
| **无遗忘机制** | 没有时间衰减（Ebbinghaus 曲线未实现），只靠 tier 与预算压 |
| **无跨域统一记忆** | 只有私信 + 自己的观看报告；桌面聊天、评论互动未接入 |
| **无冲突检测** | 两条事实矛盾时系统不主动发现，只能靠 `replaces` 人工纠正 |
| **无"此刻看到什么"快照** | 排查注入问题只能靠脚本模拟 |
| **无后台整理（dream）** | 整理靠阈值 + 手动触发，没有空闲自整理 |
| **单机单文件** | 无备份/同步（仅整理前整份备份） |

## 9. 理论依据

| 来源 | 借用内容 |
|---|---|
| 率失真综述（2026，《What to Keep, What to Forget》） | **可逆性 > 打分技巧**；多保真分层（一小块高保真 + 一大块有损） |
| MemGPT | 主上下文 + 外部存储的分页；core memory 可编辑 |
| Generative Agents | 相关性 × 近期性 × 重要性 三者分离；反思必须带证据关联 |
| A-MEM | 记忆间动态关联；新经历重组织旧记忆 |
| Ebbinghaus | 遗忘曲线（**尚未实现**） |

**必须说清楚**：用了三层架构 ≠ 复现了人类记忆。人类的遗忘、重构、情绪加权，这套一个都没实现——它只是**在工程上取了一个能长期工作的近似**。

---

## 10. 运维判据（三条）

```
① facts.md 是否仍"一句一条、≤200 汉字"
   → 又开始写小作文 = 提示词失效
② state.json 的 tasks 是否有 pending / needs_review 堆积
   → 有 = 记忆卡住，别让它继续跑
③ history 行数 是否等于收到的消息数
   → 少了 = 归档丢数据（最严重）
```

## 11. 与"持续学习"的关系（重要）

这套系统本质是**外置记忆**，它对标的是"内嵌可塑性"（真的改权重 / 改结构）。

| | 外置记忆（本系统） | 内嵌可塑性（生物） |
|---|---|---|
| 载体 | 文本文件 | 突触权重 |
| 生效方式 | 每轮注入上下文 | 结构本身改变 |
| 跨轮连续 | ✅ 有（叙事连续） | ✅ 有（因果连续） |
| 能力增长 | ❌ 不变（模型本身没变） | ✅ 会变 |
| 崩溃恢复 | ✅ 文件在就行 | ❌ 损伤不可逆 |

**结论**：

> 它模仿的是记忆的**功能**，不是记忆的**机制**。
> 它能让"她记得住"，但不能让她"变得更会"。

这是当前 AI 最真实的技术瓶颈（持续学习未解决）之下，一个**务实但有限的替代方案**——用外置结构绕开内嵌可塑性。
