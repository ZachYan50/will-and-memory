# 三层记忆：设计、实现与边界

> 初稿：2026-10-28；修订与代码核对：2026-10-29。
> 本文描述作者本机部署的 `dsh-bili-scroll` 记忆模块，核对范围为 `memory_store.py`、`memory.mjs` 和 `mcp_server.py` 的记忆接口。本仓库只有说明文档，不含完整实现或私人对话；下列参数不是所有版本的通用标准。

## 1. 要解决的不是“全部塞进去”

这个插件会在不同轮次启动新的 AI 任务进程。如果只把最近一段对话交给它，更早的约定和经历就可能无法参与这一次回答。

把所有聊天记录都放进去也不合适：单次输入的长度、处理时间和费用都有约束。反复把旧摘要压成更短的摘要，则可能丢掉后来才发现重要的细节。

我们的做法是：**长期保存的信息可以不断增加，每次只取当前需要的一部分。** 摘要帮助快速理解，原始记录负责在有疑问时提供依据。

它借用了人类记忆的直觉，但没有试图把大脑逐项复制成软件。

## 2. 用一段对话理解三层

下面是虚构例子，不是公开真实私信。

第一次聊天，对方说：“我喜欢雨夜散步，安静一点就很好。”几天后，他又解释：“上次不是因为我喜欢孤独，是因为那天很难过。”

如果系统只记“这个人喜欢孤独”，就会把自己的理解误当成事实。三层记忆应当这样配合：

| 层 | 可以留下什么 | 什么时候取用 |
|---|---|---|
| **L1 核心画像** | 少量稳定、明确的信息；一次沉默不足以写成长期性格 | 私信轮通常直接提供 |
| **L2 事实与经历** | “喜欢雨夜散步”这一结论，以及那次对话的背景、原话和后来的纠正 | 话题相关时先看梗概，再展开细节 |
| **L3 原始记录** | 两次对话实际归档的消息，供核对“当时到底怎么说” | 摘要不足、查不到或有争议时回查 |

这里的关键不只是“记得更多”，而是**保留原话与解释的区别，并允许后来的证据改变旧理解**。

## 3. 三层分别负责什么

### L1：少量随时可用的信息

L1 保存核心画像，例如明确的长期偏好。每次私信轮会读取它，不需要先搜索。

当前版本的写入和注入上限都是 **5210 个 UTF-8 字节**。这是本项目的取值，不是理论上的最佳大小。更新采用整份替换，因此模型需要保留与本次更新无关的已有内容。

提示词要求把推测放进“推测特征”标签。代码会检查格式、大小和部分措辞，但**不能自动识别所有伪装成事实的推测**，也没有给 L1 的每一行做完整来源校验。

### L2：既记结论，也记事情的经过

L2 有两类记录：

- **事实条目**：简短结论，标明是事实还是推测，并带来源。新证据推翻它时，新条目指向旧条目，旧条目保留为历史。
- **经历条目**：保存一段值得回想的事情。可以包含主题、梗概、双方观点、关键转折、逐字引文、当时的解释和未解决的问题。

同一段经历可以继续补充，但要沿用它的 ID，并带上读到的版本号。更新会形成新的当前版本，旧版本仍可读取；不是让多个互相冲突的版本同时充当当前结论。

L2 不设业务上的总条数上限。一次私信自动提供的相关卡片最多 **6144 字节**，卡片放不下的内容仍然保存在文件里，可以按需展开。

### L3：能够回查的依据

L3 保存已归档消息，每行一条，只追加。它保存收到并纳入归档的文本，不等于完整复制平台上的所有历史和媒体。

图片只留描述和来源标识，不把图片文件塞进记忆。自己的观看报告保留在另一个已有账本中，通过专门的只读工具查询；它是模型当时写下的理解，不应当被当成已核实的外部事实。

**“没有设总条数上限”不等于无限容量。** 文件仍会占用磁盘，查找仍会耗时；没有成功归档的内容，也不能靠检索凭空恢复。

## 4. 一轮对话如何使用记忆

1. **先存来源。** 宿主收到消息后归档，并记录本轮涉及的消息标识，避免重试时重复追加。
2. **准备当前上下文。** 读取 L1，按本轮话题挑选 L2 卡片，搭配最近最多 20 条消息。
3. **按需要找细节。** L2 没有相关命中时，自动尝试检索 L3，最多加入 6 条历史片段；有 L2 命中时，也可以主动展开原文核实。
4. **回复与记忆分别记账。** 发送结果和记忆提交有各自的状态。若发送已成功而记忆更新失败，应补记忆，而不是重发回复。
5. **有新证据才更新理解。** 新消息值得记住时，新增事实或补充经历；没有新内容就提交空列表，不必每轮凑数。

因此，“检索到旧事”和“把旧事升级为长期记忆”是两个动作。读到一条旧消息，不会自动修改其重要性。

一轮实际交给模型的内容还包括任务指令、当前对话和额外工具结果。**6144 字节只限制 L2 卡片，不是整轮输入大小；总成本也不是恒定的 5KB。**

## 5. 哪些事情记得更细，哪些事情这次先看

这两个问题需要分开。

**重要性**回答“以后值不值得保留”。模型参考四个方面打分：对方是否明确要求记住、是否存在约定、观点或关系是否发生转变、是否明确表达了情绪。它还必须写出判断理由。

**保留深度**回答“留多少细节”。重要经历可以保存更多背景和原话。已经保存的深层细节，不会仅因这次重要性下调就被自动删掉。

**当前相关性**回答“这次先取哪条”。一段很重要的旧事不一定与眼前问题有关；一条普通的旧事实，也可能正是这次需要的答案。

例如，聊了 200 句并不天然比聊了 20 句重要。一次明确的承诺、一次误解被纠正，可能比长时间闲聊更值得保留。

代码能要求引用本轮新消息、拒绝重复更新，并检查引用是否存在；它不能仅凭消息 ID 判断“这条新消息真的让旧事更重要”。这一层仍需要模型判断。

## 6. 怎样减少越记越偏

| 做法 | 能防住什么 | 不能保证什么 |
|---|---|---|
| 保留归档原文 | 摘要遗漏后仍有机会回查 | 搜索一定能找到，或解释一定正确 |
| 记录来源 | 能核对条目依据哪条消息或报告 | 有来源就代表推论成立 |
| 校验逐字引文 | 拒绝在指定来源中不存在的引文 | 引文没有被断章取义 |
| 保留纠正链与旧版本 | 能追溯结论怎样改变 | 自动发现所有互相矛盾的条目 |
| 搜索不增加重要性 | 避免“自己多想几遍”被计为新证据 | 模型完全不会反复误解 |
| 只合并明确选中的事实 | 避免为了总数限制而丢掉其他记忆 | 合并后的概括没有损失含义 |

自己的观看报告与联系人私信有不同的读取入口。观看报告工具不读取私信画像；但在私信里，一段经历可以同时引用观看报告和新消息。这是**有范围的来源区分**，不是所有内容永远不能交叉引用。

写入中断时，系统保留待完成记录，供下一次写操作恢复。多个文件不是在同一瞬间一起更新，因此不能只靠文件原子替换就宣称所有故障都已消除。恢复能力也以相关文件仍然完整可用为前提。

## 7. 与已有研究的关系

这些工作提供了设计参考，不是本项目效果的证明。

| 研究 | 本项目借鉴或比较的想法 | 适用边界 |
|---|---|---|
| [MemGPT，2023](https://arxiv.org/abs/2310.08560) | 把有限的当前输入与更大的外部存储分开，按需取回 | 不意味着本项目实现了相同控制流程或取得相同结果 |
| [Generative Agents，2023](https://arxiv.org/abs/2304.03442) | 按相关性、近期性与重要性选择记忆，并由经历形成更高层的总结 | 本项目采用自己的字段与排序规则，不是其完整复现 |
| [A-MEM，2025](https://arxiv.org/abs/2502.12110) | 新信息可以影响旧记忆的组织方式 | 本项目的版本更新不等于已实现论文中的完整关联网络 |
| [Colaco 与 Lahjouji，2026，预印本](https://arxiv.org/abs/2607.08032) | 讨论压缩预算、信息损失，以及保留可检索原文的价值 | 作者明确说明验证规模有限，不能推广为所有摘要系统的普遍定律 |

对最后一项，更稳妥的工程结论是：**在无法预先知道未来会问什么时，保留可回查的原文，能给遗漏的信息留一条补救路径。** 它不保证回答误差保持不变，更不能用“有多少条挤进提示词”的一次观察，证明长期错误必然按某种数学速度增长。

## 8. 当前能做什么，仍缺什么

当前实现包含分层保存、话题检索、经历版本、来源与引文检查、事实纠正，以及写入中断后的恢复路径。这些机制可以从代码核对；实际长期效果需要另外验证。

主要限制有：

- **检索可能漏掉换一种说法的旧事。** 当前依赖关键词、中文片段、主题和别名，没有使用语义向量检索。它比完整句子的精确匹配灵活，但仍不理解所有同义表达。
- **重要性和解释仍可能判断错。** 给出分数和理由，不代表系统理解了真实情绪。
- **旧记录不会自动全部提炼成经历。** 已有事实和原文保留，新经历需要在后续对话中逐步形成。
- **没有自动发现并解决所有矛盾的机制。** 也没有定时后台整理、统一接入所有聊天渠道或异地同步备份。
- **读取开销会随数据增长。** 当前部分查找需要扫描历史文件，长期使用后速度和磁盘占用都需要关注。

外部记忆不更新底层模型参数，但可以改变整个系统能取到的信息，从而改善任务表现。是否改善、改善多少，需要比较；不能说“参数没变，所以能力必然不变”，也不能把记忆效果直接解释成持续学习或意识。

## 9. 怎样检查它是否在正常工作

首先检查一件具体的旧事：能否找到对应条目，展开来源，并正确区分当时原话和后来解释。再用一条纠正消息确认旧结论不再被当作当前事实。

遇到故障时，分别检查归档、发送和记忆更新的状态。短暂的待完成状态可能只是任务正在进行；应关注长期没有推进或反复失败的记录，而不是看到一个 `pending` 就断定系统坏了。

归档完整性应按消息身份和来源核对，不能简单要求“历史行数等于收到的消息数”：历史还可能包含自己发出的回复，也会去重。迁入记录若使用本地生成的标识，应与平台原始消息 ID 区分，不能称为平台回执。

下述实现参数是代码事实，不是性能测评。本仓库目前没有提供足以复现长期召回率、错误率或多年成本的完整实验材料。

## 附录 A：给维护者的实现索引

文件按联系人 UID 分开：

```text
memory/
  L1-<uid>.md          核心画像
  <uid>.state.json     L2条目、经历版本和任务状态的主记录
  facts/<uid>.md       由主记录生成的阅读视图，不应单独修改
  <uid>.pending.json   中断写入的恢复记录
  history/<uid>.jsonl  已归档消息，一行一条，只追加
  backups/            部分更新操作前保存的备份
```

这里的 `<uid>.state.json` **不是**插件调度用的根目录 `state.json`。主记录负责 L2 和任务状态；L1、原始消息与观看报告仍有各自的存储文件。

| 参数 | 2026-10-29 核对值 | 含义 |
|---|---|---|
| L1 上限 | 5210 字节 | 当前版本写入与注入限制 |
| 自动注入 L2 卡片 | ≤6144 字节，最多12张 | 不限制已保存条目的总数 |
| 最近对话 | 最多20条 | 不意味着每条长度相同 |
| 自动 L3 历史片段 | 最多6条，每条正文最多1000字节 | L2 无相关命中时尝试 |
| 单条事实正文 | ≤600 字节 | 不是固定200个字 |
| 事实提交数量 | 提示词通常建议0–2条；代码上限30条/次 | 区分行为建议与硬限制 |
| 经历提交数量 | 最多3段/次 | 代码硬限制 |
| 经历细节预算 | 1200 / 3600 / 8000 字节 | 三档，计算细节与引文的序列化大小 |
| 关键原话 | 每段最多8条，每条≤600字节 | 必须出现在指定来源中 |

当前经历评分为四个维度之和，加上补充记录涉及的不同日期数，后者最多加2；总分达到4为中档、达到8为高档。这是工程规则，尚非经验证的人类记忆模型。日期去重也不能直接称作已经验证的“跨日巩固”。

共有9个相关接口：宿主归档 `bili_memory_ingest`；查询 `bili_memory_search`、`bili_memory_read`、`bili_memory_export`；写入与整理 `bili_memory_commit`、`bili_memory_l1`、`bili_memory_compact`、`bili_memory_promote`；观看报告查询 `bili_experience_search`。其中归档接口不提供给自动任务模型，不能把9个接口等同于每轮都可调用的9个工具。
